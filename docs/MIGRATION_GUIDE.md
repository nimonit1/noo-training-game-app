## 1. 対象読者

- Claude.ai(チャットや Artifact)でコードを書き始め、あとからクラウドセッション(Claude Code のクラウド実行)で開発を続けたい人。
- GitHub の基本操作(リポジトリ、ブランチ、コミット、プッシュ)が分かる人。

## 2. 目的

- 「どの操作を、どの順番でやっておけば、クラウドセッションで迷わず再開できるか」を一本の手順にする。

## 3. ゴール

- Claude.ai で作ったソースと成果物が、GitHub のリポジトリに入っている。
- クラウドセッションが、そのリポジトリを開いた直後から、前回の続きとして作業できる。

## 4. 目次

1. 全体像
2. 最初に1回だけやること(準備)
3. Claude.ai 側でやること(移行前)
4. GitHub に上げる
5. クラウドセッションで再開する
6. 引き継ぎファイルに書くこと
7. つまずきやすい点(今回の実例)
8. チェックリスト

## 5. 本編

### 5.1 全体像

```
[Claude.ai]            [GitHub]                [クラウドセッション]
 コード・成果物  ──→   リポジトリ  ──→   リポジトリを取り込んで再開
 (チャット/Artifact)   (ソース+引き継ぎ資料)    (README・設計書・CLAUDE.md を読む)
```

- **会話の中身は引き継がれません。** クラウドセッションが読むのは、リポジトリのファイルだけです。だから、経緯・判断・残課題を**ファイルにして**リポジトリに入れます。
- Claude.ai のセッションの作業ファイルは、そのセッション内にしかありません。GitHub に上げなければ、クラウドセッションからは見えません。
- ユーザーの「メモリ」(好み・プロジェクトの要点)は、Claude の各画面で共有されます。ただし、コードや設計書の代わりにはなりません。

### 5.2 最初に1回だけやること(準備)

順番どおりに進めてください。

| 手順 | 操作 | 確認 |
|---|---|---|
| 1 | GitHub に、空のリポジトリを作る(READMEと LICENSE だけでも可) | リポジトリの URL が分かる |
| 2 | claude.ai の設定で、GitHub を接続する(設定 → コネクタ → GitHub) | 接続済みになっている |
| 3 | **Claude の GitHub アプリを、対象のアカウント/組織と、対象リポジトリにインストールする**(`https://github.com/apps/claude/installations/select_target`) | 対象リポジトリが許可リストに入っている |
| 4 | リポジトリへの**書き込み(push)権限**が付いていることを確認する | セッションで push が通る |

- 手順3を飛ばすと、**クローンはできても push が 403 で拒否されます**。今回の脳トレ道場で、まさにこれが起きました(7.1 参照)。
- 手順4は、移行の直前ではなく、**最初のうちに**やっておくのが安全です。

### 5.3 Claude.ai 側でやること(移行前)

移行すると決めたら、Claude.ai のセッションで次を済ませます。

1. **成果物を実ファイルにする。**
   - Artifact(公開ページ)やチャット内のコードは、そのままではリポジトリに入りません。ファイルとして書き出してもらいます。
   - 依頼の例: 「いまのコードと成果物を、リポジトリに置けるファイル構成で用意して」
2. **引き継ぎ資料を作る**(6 章の内容)。
   - `README.md`(使い方・構成)、`DESIGN.md`(設計書)、`CLAUDE.md`(作業ルール)を、Claude に作らせます。
3. **動作確認をしておく。**
   - テストスクリプトがあれば、リポジトリ内のパスで動くようにしておきます(絶対パスを使わない)。
4. **機密情報が入っていないか確認する。**
   - API キー、個人情報、非公開の URL を、ファイルに残さない。外部通信の有無も、設計書に書いておく。
5. **版の管理を、ファイル名から Git に移す。**
   - Claude.ai では、文書を上書きせず、`_v1`、`_v2` のように新しいファイルで版を残していました。クラウドセッションでは、GitHub(Git)が版の履歴を持つので、**ファイル名に版番号を付ける運用はやめます**(二重管理になり、古い版のファイルが散らばるため)。
   - 旧版のファイルが複数ある場合は、最新版の内容を `README.md`、`DESIGN.md` などの1つのファイルにまとめ、旧版は削除します。旧版は Git の履歴から取り出せます(`git show <コミット>:<ファイル名>`)。移行のコミットや PR の説明に、どの版を統合したかを書きます。
   - 文書の冒頭の「改訂履歴」の表は残します。旧ファイル名は、履歴の注記として書き残します。
   - プロトタイプ(HTML)のように、版ごとに別ファイルで公開する成果物は、文書とは別に方針を決めます(このリポジトリでは `prototype/brain_dojo_v<番号>.html` を、引き続き版ごとの別ファイルにしています)。

### 5.4 GitHub に上げる

上げ方は2通りです。確実なのは A です。

#### A. セッションからリポジトリへ push する(おすすめ)

1. リポジトリをセッションに取り込む(クローン)。
2. `main` に直接ではなく、**作業ブランチ**を切る(例: `handover/initial-prototype`)。
3. ファイルを置いて、コミットする(メッセージは `type: 日本語の説明` の形)。
4. ブランチを push する。
5. GitHub 上でプルリクエストを作り、`main` に取り込む。

- 権限エラー(403)が出たら、5.2 の手順2〜4を確認します。

#### B. ファイルをダウンロードして、手元から上げる

1. セッションから、引き継ぎ一式(tar.gz や zip)をダウンロードする。
2. 手元でリポジトリをクローンし、展開したファイルをコピーする。
3. `git add`、`git commit`、`git push` する。または、GitHub の画面でファイルをアップロードする。

- 権限の設定が終わっていないときの、代替手段として使えます。今回の脳トレ道場でも、この形で一式をお渡ししました。

### 5.5 クラウドセッションで再開する

1. **新しいクラウドセッションを作り、対象リポジトリを指定する。**
   - リポジトリはセッションに取り込まれ、クローンされます。
2. **リポジトリの `CLAUDE.md` が読み込まれることを確認する。**
   - 作業ルール(言語、デザイン、版管理、外部通信の確認)は、ここに書いておけば毎回効きます。
3. **最初の依頼で、読む順番を指示する。**
   - 例(そのまま貼れます):

   ```
   このリポジトリの続きから開発を再開します。
   まず README.md、次に DESIGN.md の「5. 結論」「6. リスク・課題」「7.7 次にやること」を読んで、
   現状と次の作業を3行で要約してください。そのあと、次の作業に進みます。
   文書(README.md、DESIGN.md など)は、同じファイルを更新し、ファイル名に版番号を付けないでください。履歴は Git で管理します。
   プロトタイプは prototype/ に新しい版のファイルとして作り、既存の版は上書きしないでください。
   ```

4. **テストを一度実行して、環境が動くことを確認する。**
   - 例: `npm install` → `npx playwright install chromium` → `npm test`
5. 作業は、新しいブランチで行い、終わったらコミット・push して、プルリクエストにする。

### 5.6 引き継ぎファイルに書くこと

| ファイル | 書くこと | 役割 |
|---|---|---|
| `README.md` | 概要、動かし方、ディレクトリ構成、テストの実行方法、開発の進め方 | 最初に読む入口 |
| `DESIGN.md` | 背景、目的、目標、前提と制約、**設計判断とその理由**、リスクと課題、詳細仕様、次にやること | 経緯と判断の記録。会話の代わり |
| `CLAUDE.md` | 毎回守る作業ルール(言語、デザイン、版管理、外部通信の確認、禁止事項) | セッション開始時に自動で効く |
| `tests/` | 動作確認のスクリプトと、実行方法 | 再開時に環境が正しいかを確かめる |

書くときのコツ:

- **「なぜそうしたか」を書く。** 仕様だけだと、別のセッションが判断をやり直してしまいます。(例: 年代別メニューをやめて、目的で選ぶ方式にした理由)
- **未解決の判断を、選択肢つきで書く。** (例: ゲームを追加するか、目的を4つに統合するか)
- **未確認のことを、未確認と書く。** (例: 実機での操作感、原論文を直接確認できていない数値)
- 次にやることを、**優先順の番号つき**で書く。

### 5.7 つまずきやすい点(今回の実例)

#### 7.1 push が 403 で拒否された

- 症状: クローンと読み取りはできるが、push で「Claude doesn't have GitHub access to ... for your organization」と出る。
- 原因: Claude の GitHub アプリが、対象のリポジトリ(または組織)にインストールされていない。または、GitHub の接続が古い。
- 対処:
  1. 組織(またはアカウント)の管理者に、`https://github.com/apps/claude/installations/select_target` でアプリをインストールしてもらう。
  2. claude.ai の設定 → コネクタ → GitHub を、再接続する。
  3. その間は、5.4 の B(ダウンロードして手元から push)で進める。
- ローカルのコミットは残っているので、権限が付いたあとに、同じブランチをそのまま push できる。

#### 7.2 Artifact は、リポジトリに入らない

- Artifact(公開ページ)は、claude.ai 上に置かれたページです。リポジトリのファイルではありません。
- ソースの HTML は、ファイルとして書き出してリポジトリに入れます。公開ページの URL は、README に参考として書く程度にします。

#### 7.3 ローカルのパスで書いたテストは、クラウドで動かない

- 絶対パスや、特定の作業フォルダを前提にしたスクリプトは、別の環境で壊れます。
- リポジトリのルートからの相対パスにします(今回は `path.resolve(__dirname, '..')` に直した)。

#### 7.4 手元のパソコンのファイルは、クラウドから見えない

- クラウドセッションは、手元のファイルを直接は読めません(デスクトップアプリと連携している場合を除く)。
- 必要なファイルは、リポジトリに入れるか、セッションに添付します。

#### 7.5 出典へのアクセス制限

- 論文サイトなどが、機械的なアクセスを制限していることがあります。直接読めなかった根拠は、「報道記事に基づく」「原論文は未確認」と、設計書に書いておきます。

### 5.8 チェックリスト

#### 移行前(Claude.ai)

- [ ] GitHub のリポジトリがある
- [ ] Claude の GitHub アプリが、対象リポジトリにインストールされている(push 権限あり)
- [ ] 成果物が、実ファイルとして用意されている
- [ ] `README.md`、`DESIGN.md`、`CLAUDE.md` がある
- [ ] テストが、リポジトリ内の相対パスで動く
- [ ] 機密情報・外部通信の有無が確認されている
- [ ] 文書は、ファイル名に版番号を付けず、Git で履歴を管理している(旧版のファイルは統合して削除し、履歴の参照方法を書いた)

#### 上げる

- [ ] 作業ブランチを切った(`main` に直接コミットしていない)
- [ ] コミットした
- [ ] push が通った(通らなければ、ダウンロード+手元から push)
- [ ] プルリクエストを作り、`main` に取り込んだ

#### 再開(クラウド)

- [ ] 新しいセッションで、対象リポジトリを指定した
- [ ] `CLAUDE.md` が効いている
- [ ] 「README → DESIGN の結論・課題・次にやること」の順で読ませた
- [ ] テストが動いた
- [ ] 新しいブランチで作業を始めた

## 6. まとめと振り返り

- 順番は「**準備(GitHub 接続・アプリのインストール)→ 移行前の整理(ファイル化・引き継ぎ資料)→ ブランチで push → クラウドで再開**」です。
- 引き継がれるのは、**リポジトリのファイルだけ**です。判断の理由と、残課題を文書に残します。
- 準備(5.2)は、移行の直前ではなく、早めに済ませます。ここで止まると、再開が遅れます。

### 振り返りの質問

1. いま作っているものは、会話を消しても、リポジトリだけで続きから再開できますか。
2. 「なぜそうしたか」と「次にやること」は、文書に書いてありますか。
3. push の権限は、実際に push して確かめましたか。
